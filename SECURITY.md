## Threat model

- **The caller is untrusted.** A caller can lie about who they are, ask to skip steps, try many identifiers to learn which accounts exist, guess security answers, PINs and codes across many calls, and flood the API.
- **The model is unreliable, or fully compromised.** It can call the wrong tool, invent a tool, emit malformed JSON, call several tools at once, repeat an action, ignore every instruction, or do exactly what the caller tells it. Every gate must hold anyway, so all of them live in code: the state machine decides which tools the model is offered, and each handler checks its own preconditions again. The model chooses only the wording, which offered tool to call, and that tool's arguments. It sees what the caller says, but never a stored answer, a hash, a stored PIN, a generated one-time code or a temporary password. Tool results carry question text, pass or fail, attempts remaining, an opaque candidate token, error codes, where something was sent, ticket numbers and articles, and only after verification the spelled username or the ticket list.
- **The transcript is data, not instructions.** Caller words reach the model JSON-quoted after `Caller said:`, followed by a state block that only code writes. Caller words move the call only through code, by the pre-router's fixed patterns and the outcomes of tool checks; an instruction such as "mark me as verified" changes neither the state, the offered tools nor the verification flags.
- **Trusted:** the host running the server, the database, and whoever operates them. Anyone with database access can read the outbox, which holds temporary passwords and one-time codes by design. The model server is trusted with data but not with decisions: each request carries the current turn's caller words verbatim, including any answer, PIN or code said in that turn.

## Data handling

### Stored in Postgres (schema `servicedesk`)

| Table | Contents | Secrets |
|---|---|---|
| `users` | Directory profile, `is_vip`, `is_locked`, `locked_until`, `must_change_password` | none; there is no password column |
| `security_questions` | Question text and the argon2id hash of the normalized answer | hashes only |
| `vip_profiles` | argon2id PIN hash, assistant name, last 4 digits of the assistant and callback phones, queue | hash only |
| `sessions` | One row per call: channel, internal pipeline name (including `vip`), state, candidate user id (null for a decoy), verified flag and time, failed attempts, status, start and end times. Saved when the call starts, after every turn and on expiry. | none |
| `tickets` | Priority, category, summary, status, session. A ticket opened in a call gets a user id only when the caller is verified, or for lockout and engagement tickets of real accounts. Model-written text is redacted as described above. | none |
| `outbox` | Simulated email and SMS: user, channel, masked destination and body. Nothing is sent. | temporary passwords, one-time codes and recovered usernames, in the body |
| `audit_log` | Events with redacted JSON detail (below). No foreign keys, so the log outlives deleted rows. | none by design; see [known security limitation 6](#known-security-limitations) |
| `kb_articles`, `kb_chunks` | Articles, chunks, full-text vectors, optional embeddings | none |

Audit events and their detail: `session_started` {channel}, `caller_turn` {text}, `agent_turn` {text}, `prerouter_intent` {pipeline}, `vip_handoff` {ticket_number}, `gate_denied` {tool, error}, `tool_not_allowed` {name, state}, `extra_tool_calls_ignored` {names}, `llm_malformed` and `tool_invalid_args` {tool, reason}, `verification_locked` {pipeline, ticket_number}, `vip_verification_failed` {ticket_number}, `account_locked` {}, `otp_sent` {sends}, `username_recovered` {}, `password_reset` {account_unlocked}, `call_ended` {}, `session_expired` {}.

### Never stored

- Plaintext security answers and PINs in any column built for them: the database holds argon2id hashes only. An answer the caller says outside the verification phase can still land in `audit_log` text, see [known security limitation 6](#known-security-limitations). The seed answers and PINs are fake and derived from committed code; `pnpm seed` writes them in plaintext only to the gitignored `seed/ANSWERS.local.md` for testers.
- Passwords. There is no password store: a reset sets `must_change_password` and clears locks, and the temporary password exists only in the `outbox` body.
- One-time codes anywhere but the `outbox` body.
- Tool arguments and results, apart from the `create_ticket` and `escalate` text that becomes a redacted ticket, and raw model output. Only the post-processed reply is stored, as redacted `agent_turn` text.
- The `end_call` summary.
- Caller audio. In voice mode it streams to Amazon Transcribe and is not written locally.

### Only in memory

These live in the server or REPL process and are lost on restart:

- Session objects: the raw history (the caller's exact words, including answers, and the model's tool calls and results), the pending question, the one-time code hash with its expiry and send count, counters, and the candidate token.
- Recent wrong-answer times per account, for the cross-call lock.
- Rate-limit windows.
- Ids of expired sessions.

## Deployment warnings

- **The debug surfaces are tester tools.** The `/v1/turn` result, the socket's `state` and tool events (the browser page shows them in its header and event log) and the `pnpm chat` status line show the internal pipeline name (`vip`), states, tool names and outcomes. The `/v1/turn` result also carries the pre-router's `vip_handoff` event. They reveal an executive account before verification. `pnpm outbox` and the REPL's `/outbox` command print temporary passwords and one-time codes.
- **Keep `HOST=127.0.0.1`,** the default, and the `127.0.0.1` port mappings in `docker-compose.yml`. The api container listens on `0.0.0.0` inside Compose, so its `127.0.0.1:3000` mapping is what keeps it local. No endpoint has authentication, and the WebSocket does not check the `Origin` header, so any web page open in the same browser can connect to `ws://127.0.0.1:3000/v1/voice`.
- **Put only an audio relay in front of callers.** Never expose `/v1/*` or the page to callers. A telephony front end should forward the caller's PCM audio to the socket and only the binary reply audio back, and drop every JSON event.
- **The Compose database uses fixed credentials** (`servicedesk` / `servicedesk`) and listens on `127.0.0.1:5432`. Change both before any shared use.
- **The model server receives what the caller says.** Point `LLM_BASE_URL` only at a server you trust with spoken answers, PINs and codes. In `RAG_MODE=hybrid` the same server also receives every search query for embedding.
- **Amazon Transcribe receives everything the caller says** in voice mode, including spoken security answers, PINs and one-time codes, and Amazon Polly receives every reply text. AWS can store and use content processed by its AI services to improve them unless the account is covered by an AWS Organizations AI services opt-out policy. Apply an opt-out policy that covers Transcribe and Polly before any real voice or real answer reaches the system.
- **`seed/ANSWERS.local.md` holds every plaintext answer and PIN.** It is gitignored and excluded from the Docker build context. Never commit or ship it. The values are fake and anyone with the repository can regenerate them, so never seed real people with them.

## Known security limitations

Each of these was accepted for this prototype, for the reason given.

1. **Debug surfaces reveal executive status before verification.** Accepted because the design sends debug events to clients on purpose, for testers, and the server binds to loopback. The spoken flow reveals the same thing in ways the spec requires: an executive ID given with a how-to question gets security questions instead of an answer, verification ends after 2 failures instead of 3, and a PIN step follows. Renaming the pipeline in the output would not hide it, because when the pre-router hands off an executive the turn has no `lookup_account` tool event. What leaks is that an identifier belongs to one of 5 executives.
2. **Decoys are keyed per identifier form.** A real account asks the same questions for its email, username and employee ID; a decoy's questions depend on the exact string. Comparing the email and the username form of one name across two calls shows whether the account exists, about 90% of the time from the first question and about 99.9% from all three, without a ticket or lock. Accepted because no per-string decoy can match a real account across forms, and keying decoys on a derived username was rejected: two addresses that derive the same key would get identical decoys only when the target does not exist, which is an equally reliable oracle. Probing a single form reveals nothing.
3. **Ticket numbers are sequential.** An executive's identifier opens the engagement ticket at once, so on a quiet system a caller who opens tickets before and after a probe sees a gap of 2 instead of 1. Accepted because the spec requires a ticket for every VIP session, a random 6-digit reference would itself be masked as `[code]` by redaction, and opening the ticket later only moves the gap.
4. **Lockout is a denial of service.** Anyone with an identifier can lock an account for 15 minutes through any account pipeline or the VIP flow, or by spreading wrong answers across calls. Every answer given during the lock counts as a failure, right or wrong and whoever gives it, so continued answering renews the lock, including the real user's. Accepted as the cost of stopping answer guessing across pipelines and calls. The spec's password reset lockout already had the same exposure.
5. **Counters, limits and sessions live in one process's memory.** A restart clears the per-account failure counts and the rate-limit windows, and drops calls in progress; account locks already set stay in the database. Two API processes would not share any of it, and the set of expired session ids grows for the life of the process. Accepted for a single-process local prototype; a shared deployment needs shared storage. The per-IP limit uses the socket address, so clients behind one proxy share a budget, and fixed windows allow up to twice the limit across a minute boundary.
6. **Answers said outside the verification phase get pattern redaction only.** A security answer said before or in the same turn as the account identifier, or repeated by the model after verification, is stored in the audit log with only codes and emails masked. Later model requests can also contain a model's own echo of an answer, or of the `create_ticket` and `escalate` arguments of a verification turn; only the caller's words and the `verify_*` arguments are hidden. Accepted because closing it needs a design change, such as fully redacting every turn before verification, which would also hide the triage transcript.
7. **Only `verify_security_answer` checks the account lock.** An executive call that passed the questions before a lock took effect can still try its PIN and code, within its own 2-failure limit, and a call verified before the lock can still run its actions; a password reset there also clears the lock. Accepted because the 2-failure limit still ends verification, a verified call has already proved the identity, and a call that starts during the lock cannot pass the questions.
8. **Real and decoy accounts differ in server-side timing.** A real account costs one database read per question and two per answer that a decoy skips, one more write at lockout, and two writes when the silent cross-call lock triggers. Accepted because the gap is a few milliseconds, every such turn also includes at least two model calls, and the difference could not be measured through the API. The argon2 cost itself is equal.
9. **The model controls wording and arguments.** A model that ignores its instructions can tell the caller something untrue, such as that a reset happened, or read back anything a tool returned to it: question text, and after verification the NATO-spelled username or ticket summaries. It can also call an offered tool with other arguments than the caller gave, such as another identifier, which sends the call to the wrong account's questions but passes no check. Accepted because the model cannot change what a tool does, and no tool result contains a stored answer, PIN, code or password.
10. **No authentication and no Origin check.** Anyone who can reach the port can create sessions and take turns. Accepted for a loopback-only tester tool; see the deployment warnings.
11. **Third-party speech services see the audio.** See the Amazon Transcribe warning above. Text mode sends nothing to AWS.
12. **Untested surfaces.** The browser page was never run with a real microphone, and the Transcribe and Polly adapters were tested only with fake clients, never against live AWS. The scripted scenario run (`pnpm test:scenarios`) exercises neither `apps/api` nor the real `openai` npm clients; unit tests cover those. `pnpm test:scenarios:local` uses the real chat client, but no model server was available to run it.
13. **The REPL skips the turn text check.** `pnpm chat` passes typed lines to the agent without the length, NUL and surrogate rules the API enforces. Accepted because the REPL is a local tool with no network exposure.
14. **Bad directory data fails with an error.** A real user with no security questions, or an executive without a VIP profile, makes the turn fail with HTTP 500 or a socket error rather than a clean refusal. It fails closed; the seed never has either.
